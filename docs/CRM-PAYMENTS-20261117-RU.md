## Ежедневная работа

1. Карточка заявки → «Платежи и доли» → «+ Получить деньги».
2. Введите сумму, получателя, способ и дату. Комментарий и документ необязательны.
3. При необходимости включите детализацию: добавляйте, изменяйте и удаляйте строки. Например, получено 150 €, запчасти 30 €, колёса 20 € — остаётся 100 € нераспределённых. Это один платёж 150 €.
4. Закупку запчастей заносите отдельной операцией «Прямой расход». Продажная цена запчастей в детализации не является расходом.
5. Для старого выполненного заказа: «Завершить / исправить результат» → «Успешно выполнена», описание работ. При необходимости укажите согласованную стоимость, **новую, ещё не внесённую оплату**, расход и долю владельца.
6. Закрытие без оплаты разрешено. Оплата и выполнение независимы. Долг вычисляется при известной итоговой стоимости.
7. Владелец может исправить результат, вернуть закрытую/отменённую заявку в работу, записать позднюю оплату, расходы или изменить условия. Первоначальные записи остаются в истории; исправление денежной операции — сторно и новая операция.

Для нескольких платежей каждый раз создавайте отдельную оплату. Повтор одного запроса с тем же ключом не дублирует деньги. После потери соединения повторите отправку той же открытой формы; если форму закрыли, проверьте журнал перед новой оплатой.

Имя «другого человека» преобразуется во внутренний стабильный идентификатор. Для разных людей с одинаковым именем используйте различимые подписи. Технические ID не требуется вводить.

Доля владельца: фиксированная сумма или процент от фактически полученной выручки / выручки после расходов. Новая схема применяется только при явном выборе изменения доли; старые договорённости сохраняются. Остаток после расходов и доли владельца относится к назначенному механику. Положительный взаиморасчёт — выплатить сотруднику, отрицательный — сотрудник должен передать владельцу. Передача денег и выплата доли не являются новой выручкой.

## Telegram

Расширен существующий `/crm/bot/telegram`, новый бот не создаётся. Меню: «Мои заявки», «Сегодня», «Отчитаться о работе», «Мои отправленные отчёты», «Помощь». По номеру с несколькими обращениями нужно выбрать конкретную заявку. Список ограничен 50 строками; более старую заявку ищите по номеру.

Пошагово: проблема → выполнено → получено → способ оплаты → позиции → расходы/плательщик → итог → отправка. Кнопка «Изменить» начинает повторный ввод финансов с очисткой строк черновика. Механик видит только свои заявки. Перед отправкой назначение проверяется снова.

В карточке CRM → «Отчёты Telegram»: подтвердить или запросить исправление. Если деньги уже записаны, выберите существующий неотменённый платёж с той же суммой и получателем. Он не будет добавлен повторно. Расходы отчёта при подтверждении записываются отдельно: не дублируйте их вручную до проверки отчёта. После запроса исправления механик создаёт новый отчёт; исходный сохраняется.

Для реальной работы требуется проверить существующую конфигурацию:

- `CRM_TELEGRAM_BOT_TOKEN`: токен того же бота, который отправляет заявки AutoHelp/Liikkuva.
- `CRM_TELEGRAM_WEBHOOK_SECRET`: секрет минимум 32 символа из Secret Manager.
- `CRM_OWNER_TELEGRAM_ID`: подтверждённый личный ID владельца для уведомлений.
- В «Команда» у каждого механика указан его проверенный личный Telegram ID, сотрудник запустил бота.
- Один webhook `https://liikkuvakorjaamo.fi/crm/bot/telegram`, с `secret_token`, `allowed_updates=["message"]`, `max_connections=1`, без удаления ожидающих updates. Сначала проверить текущий `getWebhookInfo` и действующего обработчика; не перезаписывать чужой обработчик автоматически.
- Существующий защищённый `/crm/internal/tick` должен вызываться планировщиком с `CRM_INTERNAL_TOKEN`: очередь уведомлений владельцу и повторные отправки используют этот механизм. Ответы мастеру доставляются сразу, сбои остаются в очереди.

Токены не публиковать и не вставлять в переписку. В этом изменении webhook и облачная конфигурация не переключались. WhatsApp не менялся.

## Firestore

База та же: `liikkuvakorjaamo`; префикс коллекций `crm_` задаётся существующим `Collection`.

- В `crm_ledgers` добавлены `Terms.OwnerShare`, `Entries.Items`, `Entries.ParticipantName`, `Entries.Document`. Деньги — целые центы. Старые записи читаются без миграции.
- В `crm_jobs` добавлен `Outcome`. История завершения — существующая подколлекция `events`.
- `crm_jobs/{job}/completions/{request}` хранит отпечаток запроса, автора и дату для атомарной защиты от повторов.
- `crm_mechanic_reports`: предварительные отчёты и решение владельца.
- `crm_telegram_sessions`: личный пошаговый черновик.
- `crm_telegram_updates`: обработанные update_id, защита от повторной доставки.
- В `crm_outbox` добавлена строка `Keyboard` с JSON клавиатуры (вложенные массивы напрямую Firestore не поддерживает).

Новые запросы используют одиночные поля. Новые составные индексы не нужны. Существующие индексы outbox/calendar нужны как прежде. Все доступы серверные через IAM; публичный доступ к базе не открывается.

## Обновление

Сначала сохранить свои локальные изменения; команды не применяют reset/stash автоматически.

```bash
cd ~/liikkuva
git fetch origin
git switch feat/crm-payments-completion-20261117
git pull --ff-only origin feat/crm-payments-completion-20261117
python3 update.py --project=liikkuva-korjaamo --region=europe-north1 --service=liikkuva-preview --preview-only
```

Скрипт сохраняет существующую конфигурацию, собирает ревизию без трафика, проверяет health/страницы и показывает URL preview. Он не переключает основной трафик. Preview использует существующую базу: создайте отдельную тестовую заявку; не выполняйте тестовые финансовые операции на клиентских заказах.

Проверить в preview: простую оплату, детализацию, закрытие без оплаты, повтор открытия, финансовую историю; доступ механика. После успешной проверки:

```bash
python3 update.py --project=liikkuva-korjaamo --region=europe-north1 --service=liikkuva-preview --resume
```

`--resume` повторно проверяет последнюю проверочную ревизию и переключает трафик без пересборки. Если параллельно разворачивали другой код, сначала сверить имя ревизии.

## Откат

До публикации сохранить имя прежней производственной ревизии:

```bash
gcloud run services describe liikkuva-preview --project=liikkuva-korjaamo --region=europe-north1 --format='table(status.traffic.revisionName,status.traffic.percent,status.traffic.tag)'
```

Вернуть 100% на сохранённую ревизию командой `gcloud run services update-traffic ... --to-revisions=ИМЯ_СТАРОЙ_РЕВИЗИИ=100`. Если Firebase Hosting привязан к тегу, этот тег также нужно вернуть на старую ревизию. Не удалять Firestore-документы и не откатывать базу целиком.

**После отката старого кода приостановить изменение финансов и Telegram-отчётов:** старый сериализатор может удалить новые поля при перезаписи документа. Уже сохранённые данные остаются в Firestore, пока их не перезаписывает старая версия. Для продолжения финансовых операций нужен исправленный совместимый релиз, а не старая форма.
