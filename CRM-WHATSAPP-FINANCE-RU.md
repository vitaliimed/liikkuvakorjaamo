# Платежи, распределение и WhatsApp: состояние версии

Дата: 10.11.2026. База остаётся `liikkuvakorjaamo`. Основной сайт, форма, старые документы и `Report.ReceivedCents` не изменяются этой доработкой.

## Финансы: реализовано

Владелец открывает «Платежи и доли» из меню или карточки заказа. `GET/POST /crm/api/jobs/{id}/ledger` — отдельный журнал `crm_ledgers/{jobID}`. Механикам API запрещён; они продолжают заполнять свой технический отчёт.

- Окончательная сумма, дата выполнения, дата счёта и срок оплаты задаются явно. Согласованная сумма берётся из Agreement, для старых подтверждённых заказов — Proposal. Первоначальная окончательная сумма является предварительной до сверки владельцем.
- `payment`: деньги клиента, дата, способ, фактический получатель. Частичные платежи поддерживаются.
- `refund`: фактический возврат клиенту; не изменяет окончательную стоимость сам по себе. Если цена ремонта также уменьшена, отдельно измените окончательную сумму с основанием.
- `expense`: прямой расход. Расход, оплаченный участником кроме `owner`, дополнительно увеличивает сумму к возмещению этому участнику.
- `remittance`: владелец подтверждает получение денег, ранее собранных сотрудником. Это не второй платёж клиента.
- `payout`: выплата начисленной доли участнику. `reimbursement`: возмещение его прямых расходов. Это разные операции.
- `reverse`: полное сторно денежной операции; оригинальная запись сохраняется. Для исправления суммы сначала сторнируйте, затем добавьте правильную операцию. Повторное сторно запрещено. Зависимые перечисления отменяются прежде исходного платежа.
- `terms`: новая версия суммы, дат и распределения; прежняя версия остаётся в журнале.
- Каждая операция содержит постоянный ключ, автора, фактическую дату, время регистрации и основание. Повтор с тем же ключом и данными не добавляет деньги. Другие данные при том же ключе дают конфликт. Firestore-транзакция проверяет версию и атомарно сохраняет журнал.
- Лимиты: 500 записей и 600 КБ JSON на один заказ; превышение явно отклоняется, ничего не обрезается. Архивирование больших журналов ещё не реализовано.

### Правила расчёта

Все суммы — целые центы EUR. `owner` — постоянный ID владельца для распределения; механики используют ID из карточки сотрудника; допускаются другие постоянные ID участников.

1. Валовой результат = окончательная стоимость − прямые расходы.
2. Денежный результат = оплаты − возвраты − прямые расходы.
3. Фиксированные доли начисляются в заданном размере, в том числе при убытке.
4. Проценты применяются к положительному остатку после расходов и фиксированных долей. Ввод 40% хранится как 4000 базисных пунктов. Сумма процентов не больше 100%.
5. Округление вниз до цента; остаток явно показан как «Не распределено». При превышении фиксированных долей над прибылью остаток отрицательный.
6. К выплате участнику = начисленная доля − выплаты. Отрицательное значение означает аванс/переплату, не обнуляется автоматически.
7. Деньги, собранные у клиента, и начисленная доля сотрудника не взаимозачитываются автоматически. Для удержания доли из собранных денег явно отразите согласованные операции; автоматический netting не реализован.
8. Долг клиента = max(0, окончательная сумма − оплаты + возвраты). Переплата показана отдельно. Просрочка считается после срока оплаты по Europe/Helsinki.

`GET /crm/api/ledger-report?brand=liikkuva&mechanic=ID&from=2026-11-01&to=2026-11-30`:
полный список заказов, общая сводка, группы брендов/механиков, доли и выплаты участников, денежная динамика по дням/месяцам. Период ограничивает денежную динамику; текущие остатки остаются за всё время и так подписаны в интерфейсе. Это управленческий учёт, не банковская сверка или налоговый расчёт. Отчёт читает все подходящие заказы и их журналы; при большой базе потребуется агрегирование для снижения числа чтений.

### Исторические отчёты

Автоматического импорта платежей нет. Сумма `Report.ReceivedCents` показана отдельно для сверки. Владелец может добавить `legacy_payment` с проверенной датой, получателем и основанием. Сервер сверяет сумму с отчётом и запрещает такой импорт, если в заказе уже записан обычный или исторический платёж. Повторный импорт после сторно также не допускается — дальнейшая корректировка выполняется обычными операциями с основанием. Существующие документы не удаляются и не перезаписываются миграцией.

## WhatsApp: реализовано в коде

Рабочий номер: `+358413606032`. Владелец видит кнопку открытия WhatsApp с финским текстом предложения. Это открытие приложения, **не серверная отправка**: владелец выбирает рабочий аккаунт и нажимает «Отправить» в приложении. CRM не считает сообщение отправленным до получения подтверждающего события.

`Server.IngestWhatsApp(ctx, config, originalBody, signature)` — Go-интерфейс для существующего gateway. Он **ещё не подключён к работающему gateway**, которого нет в этой ветке. Новый публичный Meta webhook не создавался.

- Проверка HMAC-SHA256 исходного тела, WABA ID и Phone Number ID.
- Нормализация входящих `messages`, исходящих из приложения `smb_message_echoes`, истории `history`.
- Дедупликация по Phone Number ID + message ID, включая доставку одного сообщения через history и echoes.
- Статусы, полученные до сообщения; delivered/read не понижаются старым sent. Статус обновляется также в сообщении привязанного заказа.
- Исходные подписанные payload сохраняются в приватной коллекции `crm_whatsapp_events`, сообщения — в `crm_whatsapp_inbox`.
- Вложения: сохраняются provider media ID, MIME, hash, filename и подпись. **Сами бинарные файлы ещё не скачиваются в bucket.** Ссылки `whatsapp-media:` являются идентификаторами, а не публичными URL.
- `GET /crm/api/whatsapp` — owner-only страницы по 100 записей с курсором. Пока упорядочено по ID, а не по времени.
- `POST /crm/api/whatsapp {id,job_id}` — явное подтверждение привязки конкретного сообщения владельцем + проверка совпадения международного номера клиента в заказе. Одинаковый телефон не вызывает автоматической привязки, повторная привязка к другому заказу запрещена.
- Привязанные сообщения попадают в существующую `crm_jobs/{id}/messages`, с vehicle_id и оригиналом. Текущий язык берётся из карточки заказа; уже существующий TranslateMessage может сохранить русский перевод отдельно. Провайдер перевода по-прежнему не подключён.
- Механики не имеют доступа к inbox, клиентской переписке и финансовому журналу.

## Что НЕ подключено / остаётся сделать

- Проверить доступность Coexistence для конкретного Meta-аккаунта через Embedded Signup; наличие установленного Business App само по себе не подтверждает eligibility. Нельзя удалять приложение или выполнять обычную миграцию с отключением App.
- Подключить реальный gateway к IngestWhatsApp, передавая **неизменённое тело и оригинальную подпись**. Адаптер ожидает Meta envelope; обёртка BSP требует отдельного проверенного адаптера. Не пересобирать JSON до проверки подписи.
- Подписать существующий webhook на поддерживаемые messages/echoes/history/state events и проверить настоящие события на тестовом диалоге. Полученные raw state/edit/revoke сохраняются, но редактирование и отзыв уже показанного текста ещё не проецируются в интерфейс.
- Payload больше 500 КБ требует отдельного хранения/потокового разбора в gateway. Текущий адаптер отклоняет его; нельзя подтверждать такой webhook как обработанный. Не пытаться разбивать подписанное тело без отдельной проверки подписи и доверенного адаптера.
- Реализовать скачивание оригиналов медиа в приватный bucket и owner-only выдачу бинарных вложений.
- Подключить переводчик FI/EN→RU.
- Серверная отправка через Cloud API и утверждённые шаблоны ещё не реализована. Первое сообщение вне сервисного окна требует шаблона; сейчас отправка подтверждается в Business App. Нет автоматической отправки, клиентского бота или фонового sender.
- Нет выполненного подключения Meta, реального теста синхронизации или развёртывания новой Cloud Run revision. В текущем рабочем окружении отсутствуют gcloud и авторизованный доступ к Google Cloud.

Форматы сверены с документацией поставщика: https://docs.360dialog.com/partner/onboarding/whatsapp-coexistence/coexistence-webhooks и https://docs.360dialog.com/partner/onboarding/whatsapp-coexistence . Это справка о протоколе, не выбор платного провайдера и не подтверждение доступности вашего аккаунта. Страница Meta при проверке отвечала HTTP 429.

## Обновление Preview из Cloud Shell

```bash
(
  set -e
  cd "$HOME/liikkuva"
  if [ -n "$(git status --porcelain)" ]; then
    echo 'Есть локальные изменения. Сохраните их перед обновлением.'
    git status --short
    exit 1
  fi
  git fetch origin
  if git show-ref --verify --quiet refs/heads/feat/crm-complete-v2; then
    git switch feat/crm-complete-v2
    git pull --ff-only origin feat/crm-complete-v2
  else
    git switch --track origin/feat/crm-complete-v2
  fi
  python3 scripts/deploy-crm-preview.py
)
```

Существующий скрипт запускает Go-тесты, UI-тесты и сборку, создаёт revision с `--no-traffic`, сохраняет основной трафик и печатает фактический Preview URL. Отправка email отключена в Preview. Эмуляторные тесты без FIRESTORE_EMULATOR_HOST пропускаются; перед коммитом они запускаются отдельно с локальным эмулятором. Настоящий номер WhatsApp и Firestore production в локальных тестах не используются.
