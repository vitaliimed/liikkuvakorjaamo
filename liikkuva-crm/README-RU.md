# Liikkuva CRM — первая реализация для установки и приёмки

Дата: 08.11.2026. Стек: Go, Firestore, приватный Google Cloud Storage, обычный HTML/CSS/JS. Это исходный код и проверяемая сборка; **в вашем Google Cloud проекте CRM пока не развёрнута**, реальные пользователи и бот не подключены. `CRM-preview.html` показывает интерфейс с вымышленными данными и не сохраняет изменения.

## Что реализовано

- Отдельные аккаунты владельца, менеджера и механика. Механик получает доступ к своим обращениям. Владелец управляет аккаунтами и отключает доступ. Пароли хешируются bcrypt; сессия живёт 12 часов. Смена пароля и отключение аккаунта делают прежнюю сессию недействительной.
- Нормализованный номер автомобиля: `ABC-123`, `abc 123`, `ABC123` объединяются. Техническая история доступна механику через назначенное ему обращение; чужие контакты и переписка скрыты. Номер — основной ключ поиска; для смены номера или иностранной регистрации потребуется отдельная модель идентификаторов. Сейчас страна по умолчанию FI.
- Каждое обращение отдельно: источник Liikkuva/AutoHelp, клиент, телефон, адрес, язык, проблема, даты, исполнитель, согласование, стоимость, фактическая оплата, результат, оставшиеся работы.
- План выезда: дата, начало, длительность, стоимость выезда/работ/запчастей, способ оплаты, обязательный план ремонта и необязательная причина поломки.
- Начальные цены: **50 € выезд + 70 € диагностика и ремонт = 120 €**, запчасти отдельно. Это начальные значения CRM, механик меняет их до согласования. Цены существующего лендинга установщик не меняет: проверьте, чтобы клиент видел непротиворечивые условия.
- Согласие клиента записывается менеджером с текстом сообщения или результатом звонка. Только после этого менеджер подтверждает выезд. Перенос требует нового согласования.
- Общий календарь в CRM, календарь своих выездов у механика; часовой пояс Europe/Helsinki, хранение времени UTC. Проверка пересечений через транзакцию Firestore. Длительность учитывается, время на дорогу механик включает сам.
- Отчёт: сколько получили, способ оплаты, выполненные работы, результат «отремонтировано / частично / не отремонтировано». Для незавершённого ремонта обязателен следующий шаг. Финальное закрытие — после проверки менеджером.
- До 10 ремонтных фото на обращение: можно выбрать несколько файлов; JPEG/PNG, каждый до 5 МБ, до 60 MP. До/в процессе/после, подпись, автор, время загрузки и SHA-256. Оригиналы не изменяются, файлы выдаются только через авторизованный API. HEIC/WebP пока не принимаются: экспортируйте в JPEG.
- История действий и снимки состояния при изменениях. Записи не перезаписываются через интерфейс. Это журнал приложения, **не независимое неизменяемое доказательство**: администратор GCP с доступом к базе может менять данные. Время фото — время загрузки, не подтверждённое время съёмки.
- Переписка сохраняется вручную с каналом и направлением. Входящая, исходящая уже отправленная, внутренняя заметка. Автоматического импорта WhatsApp/Telegram-переписки нет.
- Готовое предложение клиенту на FI/EN/RU. Личное уведомление владельцу содержит номер клиента, ссылку на заявку и текст. CRM не пишет клиенту автоматически.
- Telegram webhook: механик пишет номер авто в личный чат с ботом, получает доступные обращения и ссылки. **Отчёт и фото он заполняет в мобильной форме CRM**, а не в пошаговом чате. Вход в CRM обязателен.
- Очередь уведомлений в Firestore; обработчик отправки с повторными попытками. Отдельная плановая задача создаёт напоминания за час. Устаревшие предложения/напоминания подавляются по состоянию заявки. Возможны редкие повторные сообщения при сбое после отправки в Telegram и до отметки в базе — доставка at-least-once.
- Версионирование записи защищает от потери параллельных изменений. После конфликта обновите карточку.
- API приёма лидов для будущего AutoHelp и других систем с токеном и ключом идемпотентности.

## Порядок работы

1. Приходит заявка → новая карточка обращения с автомобилем.
2. Вы назначаете механика.
3. Механик предлагает время, длительность, цену и план работ.
4. CRM сохраняет предложение и ставит личное уведомление вам в очередь.
5. Вы отправляете клиенту готовый текст на указанный номер.
6. Получив ответ, записываете согласие клиента.
7. Подтверждаете выезд → он появляется в календаре, механику приходит уведомление.
8. Механик отмечает начало работ.
9. После визита добавляет сумму, результат, что сделал и что осталось, фотографии.
10. Вы проверяете отчёт и закрываете обращение или возвращаете его в работу.

Для повторного визита создавайте новое обращение с тем же номером. Так не смешиваются разные даты, оплаты и договорённости.

## Данные и расходы

Cloud Run исполняет приложение; постоянные данные находятся в Firestore, фото — в приватном bucket. Не храните базу или оригиналы фото на файловой системе Cloud Run: она временная.

Коллекции: `crm_jobs`, `crm_jobs/{id}/events`, `crm_users`, `crm_sessions`, `crm_schedules`, `crm_outbox`, `crm_login_limits`. Существующие `leads`, настройки сайта и письма сохраняются.

Списки запрашиваются порциями по 100; история также с пагинацией. Фоновый бесконечный опрос из браузера отсутствует. Показатели на главной относятся к загруженным обращениям; для всей базы загрузите все страницы. Календарь тоже показывает загруженные записи. Для большого объёма нужны серверные агрегаты/фильтры дат.

Стоимость зависит от числа операций, фотографий, трафика и резервирования. Фиксированный бюджет не обещается. Для вашего небольшого потока отдельный Cloud SQL в этой реализации не нужен. Настройте бюджетные уведомления в GCP, резервные копии Firestore и защиту/сроки хранения фото. Эти настройки не выполнялись из чата.

## Установка в существующий проект — рекомендуемый вариант

Архив содержит **новый модуль CRM и точечный установщик**, а не старую копию всего сайта. Это позволяет сохранить ваши более поздние изменения.

После распаковки в Cloud Shell:

```bash
cd "$HOME/liikkuva-crm"
python3 install.py "$HOME/liikkuva"
cd "$HOME/liikkuva"
go test ./...
```

`install.py` проверяет имя Go-модуля и ожидаемые точки интеграции. Если структура актуального проекта отличается, он останавливается до изменения исходников. Изменяет `router.go` и сохранение лида в `services_firestore.go`, добавляет `crm_bridge.go` и `crm/`. Резервная копия — в `.crm-backup-<дата>` внутри проекта. Не удаляйте её до приёмки. При повторной установке создаётся новая резервная копия.

Встроенная интеграция сохраняет старую заявку сайта и CRM-обращение **одним атомарным batch**. Если CRM-данные невалидны, заявка не подтверждается как сохранённая. Поэтому перед переключением трафика обязательно проверьте отправку реальной формы с телефонами, адресами и номерами, которые вы принимаете. Старые заявки не импортируются автоматически.

Существующий Go module уже включает Google Cloud SDK и x/crypto; после установки может потребоваться `go mod tidy` на актуальной версии Go. Наш самостоятельный пакет имеет собственные проверенные `go.mod`/`go.sum`; **не заменяйте ими go.mod живого сайта**.

## Обязательные настройки перед запуском

| Переменная | Назначение |
|---|---|
| `CRM_PHOTO_BUCKET` | Отдельный приватный bucket только для ремонтных фото |
| `CRM_OWNER_EMAIL` | Ваш email для входа; задаётся вами |
| `CRM_OWNER_PASSWORD` | Первоначальный пароль, 12–72 байта; Secret Manager |
| `CRM_PUBLIC_URL` | Полный origin CRM без завершающего `/`, например HTTPS-адрес preview или основного сайта |
| `CRM_TELEGRAM_BOT_TOKEN` | Токен отдельного Telegram-бота CRM; Secret Manager |
| `CRM_OWNER_TELEGRAM_ID` | Ваш личный числовой Telegram ID, не группа |
| `CRM_TELEGRAM_WEBHOOK_SECRET` | Случайный секрет от 32 символов; Secret Manager |
| `CRM_INTERNAL_TOKEN` | Секрет от 32 символов для обработчика очереди/напоминаний |
| `CRM_INTAKE_TOKEN` | Отдельный секрет от 32 символов для будущих интеграций |

При интеграции используется существующий `FIRESTORE_PROJECT_ID` и база `liikkuvakorjaamo`. Для самостоятельного сервера: `GOOGLE_CLOUD_PROJECT`, `CRM_DATABASE` (по умолчанию `liikkuvakorjaamo`) и `SITE_URL`.

`CRM_OWNER_PASSWORD` создаёт владельца только если его ещё нет, повторный запуск не сбрасывает пароль. Email в аккаунте — идентификатор. Владелец добавляет механиков и менеджеров в разделе «Команда». Сброс пароля владельца по email и MFA в эту версию не входят; до запуска нужен согласованный административный способ восстановления доступа.

**Используйте отдельный бот CRM.** Не меняйте webhook бота, который уже обслуживает другой проект: у одного Telegram-бота один активный webhook. Бот WhatsApp из предыдущей задачи здесь не подключён и не изменён.

Для фотографий создайте новый bucket с uniform bucket-level access и public access prevention. Не используйте прежний bucket лендинга, если у него есть общая очистка или публичные разрешения. Сервисному аккаунту Cloud Run нужны доступ к Firestore (`roles/datastore.user`), доступ только к CRM-bucket (`roles/storage.objectAdmin`) и чтение используемых секретов (`roles/secretmanager.secretAccessor` на конкретных секретах). Не выдавайте эти права браузеру/клиентскому JS.

Правила Firestore должны запрещать прямое клиентское чтение `crm_*`. Сервер работает через IAM. Приложенный `firestore.rules` — пример **для отдельной базы**, не перезаписывайте им правила общей базы без проверки существующих функций. В частности, существующее широкое `allow read, write: if true` нельзя исправить добавлением отдельного deny: разрешения правил объединяются.

Создайте составные индексы из `firestore.indexes.json` в базе `liikkuvakorjaamo`. Каждый индекс можно создать командой:

```bash
gcloud firestore indexes composite create \
  --project=liikkuva-korjaamo \
  --database=liikkuvakorjaamo \
  --collection-group=crm_jobs \
  --query-scope=collection \
  --field-config=field-path=Status,order=ascending \
  --field-config=field-path=Proposal.Start,order=ascending
```

Это пример только для напоминаний. Остальные поля и направления перечислены в JSON; дождитесь готовности всех индексов. Эмулятор не заменяет проверку индексов в настоящем Firestore.

## Preview в Cloud Run

1. Сначала настройте приватный bucket, права сервисного аккаунта, секреты и индексы.
2. Обновите CRM-переменные и привязки Secret Manager для нового развёртывания. Сохраняйте остальные настройки сайта.
3. Соберите исходники в новую ревизию без трафика:

```bash
gcloud run deploy liikkuva-preview \
  --project=liikkuva-korjaamo \
  --region=europe-north1 \
  --source="$HOME/liikkuva" \
  --no-traffic \
  --tag=crm-preview
```

Это шаблон команды развёртывания **после настройки env/secrets**, он сам не создаёт их. Не вставляйте пароли и токены в переписку, исходники или Git.

4. Получите фактический URL тега через `gcloud run services describe`. Установите `CRM_PUBLIC_URL` именно в этот origin при тестировании тега: защита Origin отклоняет отправку с другого домена. После окончательного переключения задайте основной HTTPS origin. Отсутствующий `CRM_PUBLIC_URL` в интеграции использует существующий `SITE_URL`.
5. Откройте `<фактический URL>/crm/` и выполните приёмку ниже. Без настройки базы/секретов один только интерфейс не означает рабочую CRM.
6. Переключайте production-трафик только на проверенную ревизию. Не применяйте старый архив всего сайта поверх актуального репозитория.

## Бот и напоминания

Webhook URL: `<CRM_PUBLIC_URL>/crm/bot/telegram`.

Настройка Telegram `setWebhook` должна содержать `url`, `secret_token=CRM_TELEGRAM_WEBHOOK_SECRET`, `allowed_updates=["message"]`. Токен и webhook secret не публикуйте. Ответы бота сохраняются в очередь, поэтому плановый обработчик обязателен.

Cloud Scheduler: POST `<CRM_PUBLIC_URL>/crm/internal/tick`, заголовок `Authorization: Bearer <CRM_INTERNAL_TOKEN>`, раз в минуту. Плановая задача принадлежит этому CRM-проекту и не связана со старым новостным ботом. Не включайте её до готовности бота и индексов. Ошибки/попытки видны в «Уведомления»; там же есть ручная обработка очереди. Встроенные напоминания создаются для подтверждённых выездов в ближайший час. При простое Scheduler напоминания могут не прийти.

Telegram: каждый сотрудник сначала открывает бота и нажимает Start. Владелец записывает его личный числовой Telegram ID в карточку сотрудника. Один ID должен принадлежать одному активному сотруднику: при неоднозначном сопоставлении бот не выдаёт данные. Групповые чаты не обрабатываются.

Экспорт `.ics` — файл с напоминанием за час. Это не живая синхронизация Google Calendar; переносы нужно обновлять отдельно. Источник актуального расписания — CRM.

## API для AutoHelp

`POST /crm/api/v1/leads`

Заголовки:
- `Authorization: Bearer <CRM_INTAKE_TOKEN>`
- `Idempotency-Key: <уникальный ID заявки, 16–128 символов>`
- `Content-Type: application/json`

```json
{
  "plate": "ABC-123",
  "name": "Имя клиента",
  "phone": "+358401234567",
  "email": "",
  "address": "Адрес выезда",
  "description": "Автомобиль не запускается",
  "brand": "autohelp",
  "language": "fi"
}
```

Повтор с тем же ключом возвращает прежнюю заявку. Никогда не переиспользуйте ключ для другого обращения. Это серверный секрет: не помещайте его в публичный JS сайта. В текущей версии endpoint принимает текст заявки; для файлов требуется отдельная авторизованная интеграция. AutoHelp ещё не подключён.

Остальные API v1-функции для внешних партнёров, OAuth/scopes, синхронизация WhatsApp и переводы свободной переписки потребуют следующего этапа. Текущие `/crm/api/jobs`, `.../actions`, `.../photos`, `.../events` используются собственным интерфейсом через пользовательскую сессию.

## Импорт старых заявок

Запускается из этого пакета, не из папки лендинга:

```bash
go run ./cmd/import-leads --project liikkuva-korjaamo
# Сначала изучите результат проверки. После резервного копирования:
go run ./cmd/import-leads --project liikkuva-korjaamo --apply
```

По умолчанию только проверка. Применение идемпотентно по ID исходной заявки. Сохраняется исходная дата обращения. Исторические заявки импортируются как новые для ручного разбора, без выдуманных отчётов, оплат и согласований. Некорректные номера и отсутствующие обязательные контакты пропускаются с указанием ID; их нужно исправить отдельно. Старые фотографии остаются в прежнем хранилище/админке — приватная миграция старых файлов не выполняется.

## Приёмка до реальной работы

- Владелец входит, создаёт механика и менеджера; отключённый сотрудник теряет доступ.
- Два механика: чужая заявка/переписка недоступны, техническая история назначенного автомобиля доступна.
- Заявка с реальной формы сайта создаёт одну связанную CRM-запись; ошибка сохранения не выглядит как успех.
- Предложение механика → личное сообщение владельцу с правильным номером клиента и ценами.
- Без согласия клиента подтвердить выезд нельзя; два пересекающихся выезда одного механика нельзя подтвердить.
- Проверить календарь, смену даты и часового пояса, повторное согласование после переноса.
- Получить реальное напоминание из Scheduler и проверить ошибку отправки/повторную попытку.
- Загрузить 10 фото, отклонить 11-е; проверить доступ с другого аккаунта и без входа.
- Частичный ремонт без следующего шага не сохраняется; оплата не теряет копейки.
- Перезапуск/новая ревизия Cloud Run не удаляет данные; проверить восстановление из резервной копии.
- Отдельно проверить ограничения существующих middleware, Firebase Hosting rewrites и CDN: `/crm/**` должен доходить до Cloud Run, не кэшироваться и не заменяться лендингом.

## Ограничения первой версии

Нет живой интеграции WhatsApp, автоматического перевода входящей переписки, диалога заполнения отчёта внутри бота, выставления счетов/налогового учёта, онлайн-оплаты, MFA, восстановления владельца по email, автоматической синхронизации внешнего календаря, политики удаления/экспорта персональных данных через UI и независимой неизменяемости журнала. Платежи в CRM — записи механика, не подтверждение банка. До эксплуатации требуется настроить хранение/резервирование и пройти облачную приёмку.
